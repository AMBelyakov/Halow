# Видео между двумя платами T-Halow с просмотром в браузере

> **Устарело (схема до сентября 2026).** Здесь описан первый вариант: UART 115200,
> `AT+TXDATA`, видео через RJ45 модуля. Он не работает на прошивке модуля 2.4.1.3 и
> заменён прозрачным UART 3 Мбод (`uart_p2p`) с доставкой по USB приёмника в
> `tools/halow_viewer.py`. Актуальное описание — `checkpoints/release_2026-10-08/README.md`,
> таблица решений — `docs/vkr/features_table.md`, ход работы — `docs/halow_link_debug.md`.

## Как это устроено

```
[плата 1: камера]                          эфир            [плата 2: приёмник]        [ПК]
 ESP32-S3 --UART 115200--> TX-AH (STA)  ~~HaLow~~>  TX-AH (AP) --RJ45--> сетевая карта
   JPEG                    AT+TXDATA                мост в Ethernet        halow_viewer.py
                                                                                 |
                                                                          http://localhost:8099
```

Ключевой момент: **приёмный ESP32 в передаче видео не участвует.** Модуль TX-AH в штатной
прошивке — это Ethernet-мост, он сам выкладывает принятые из эфира кадры в свой порт RJ45
(PHY IP101G на плате подключён к модулю, а не к ESP32 — у ESP32-S3 попросту нет Ethernet-MAC).

Поэтому камера отправляет не «сырой JPEG», а готовые Ethernet + IPv4 + UDP пакеты:
`AT+TXDATA` в штатной прошивке (режим «один-ко-многим») и так требует 14-байтный
Ethernet-заголовок перед данными. Мы просто дописываем к нему настоящие IP и UDP заголовки —
и ПК получает обычные UDP-датаграммы. Никакого Npcap и прав администратора не нужно.

Прошивка приёмника нужна только чтобы поднять модуль в режиме AP и отдавать RSSI со своей
стороны линка.

## Узкое место и реальные ожидания

UART между ESP32 и модулем жёстко работает на 115200 (~11 КБ/с) — это и есть потолок всей
цепочки, а вовсе не радиоканал. Отсюда:

| Разрешение | Размер JPEG | Ожидаемо |
| :--------- | :---------- | :------- |
| 96×96      | 2–4 КБ      | 3–4 fps  |
| 160×120 (QQVGA) | 3–5 КБ | 2–3 fps  |
| 320×240 (QVGA)  | 7–10 КБ | ~1 fps  |

Крутится в [HalowVideo_STA.ino](../examples/HalowVideo_STA/HalowVideo_STA.ino): `FRAME_SIZE`
и `JPEG_QUALITY` (больше число — сильнее сжатие и выше fps).

## Прошивка плат

Обе платы шьются одним и тем же проектом, переключая `src_dir` в `platformio.ini`:

1. **Плата с камерой.** В `platformio.ini` оставить `src_dir = examples/HalowVideo_STA`,
   собрать и залить через Type-C.
2. **Приёмная плата.** Раскомментировать `src_dir = examples/HalowVideo_AP` (а STA
   закомментировать), собрать и залить.

`HALOW_SSID` и `HALOW_BSS_BW` в обоих скетчах должны совпадать. Модули подключатся сами,
`AT+PAIR` не нужен: у обоих задан один SSID и шифрование выключено (`AT+KEYMGMT=NONE`).

Проверить можно по Serial-монитору: камера раз в 2 секунды печатает строку вида
`[связь] RSSI -47 dBm | 3.4 fps | 9.8 КБ/с`.

## Настройка ПК

1. Патч-корд из **RJ45 приёмной платы** в сетевую карту ПК.
2. Этой сетевой карте задать статический адрес: **10.10.10.1**, маска **255.255.255.0**,
   шлюз пустой.
3. Запустить просмотрщик:

```bash
python tools/halow_viewer.py
```

Брандмауэр Windows спросит разрешение для Python — разрешить (нужен приём UDP).
Открыть **http://localhost:8099**.

Если порт 8099 занят: `python tools/halow_viewer.py --http-port <другой>`.

### RSSI со стороны приёмника

Камера кладёт свой RSSI в заголовок каждого кадра, поэтому он виден всегда. Чтобы увидеть ещё
и RSSI, который меряет приёмник, подключите плату AP к ПК по USB и запустите:

```bash
python tools/halow_viewer.py --serial COM7     # свой номер порта
pip install pyserial                            # если ещё не стоит
```

## Что показывает страница

RSSI обеих сторон, fps, битрейт, разрешение, размер кадра, счётчики принятых и потерянных
кадров, процент потерянных пакетов.

## Если видео нет

Проверяйте по цепочке:

1. **Связь модулей.** Serial-монитор камеры: если пишет `нет связи` — модули не соединились.
   Сверьте `HALOW_SSID` и `HALOW_BSS_BW`, убедитесь что модули на одной частоте
   (`AT+FREQ_RANGE?`), при большом расстоянии поднимите `AT+ACKTMO`.
2. **Кадры уходят.** В мониторе камеры должны расти fps и КБ/с. Если `чанк не ушёл` — модуль
   не отвечает `OK` на `AT+TXDATA`.
3. **Пакеты долетают до ПК.** Wireshark на нужном интерфейсе, фильтр `udp.port == 5000`.
   Если пакеты видны, а страница пустая — брандмауэр блокирует Python.
4. **Ничего не долетает по UDP.** Так и есть на практике: мост AP **не выпускает** в RJ45
   кадры, которые STA инжектировала через `AT+TXDATA` (адаптер на ПК показывает «Принято: 0»),
   хотя на UART приёмника те же кадры исправно приходят как `+RXDATA` — диагностика показала
   растущий счётчик. Поэтому доставку ведём через **USB приёмника** (это рабочий путь):

   ```
   эфир → модуль AP → UART(+RXDATA) → ESP32 (HalowVideo_AP) → USB → ПК
   ```

   `HalowVideo_AP` вычленяет из `+RXDATA` наш прикладной пакет и гонит его в USB-Serial
   с простым кадрированием (`[0xA5][0x5A][type][len16][payload]`, см. `lib/HalowVideo/halow_proto.h`).
   Запускайте просмотрщик так:

   ```
   python tools/halow_viewer.py --serial-video COMx
   ```

   Скорость USB CDC номинальна (не 115200), так что форвардинг не тормозит — единственный
   потолок остаётся на UART камера↔модуль. UDP-путь оставлен на случай прошивки модуля,
   которая мост всё-таки включит.

## Если нужно больше fps

Единственный способ поднять потолок — уйти от AT-режима на прозрачную прошивку модуля.
В `SDK/` уже лежат готовые бинарники `huge-ic-ah_..._wnb_uartp2p_baud_460800.bin` и др.:
при 460800 бод получится ~45 КБ/с, то есть QVGA ~5 fps или 160×120 ~12 fps.

Цена вопроса:

- Прошить модуль можно только вынув SOP8-флешку из панельки и залив её программатором
  (см. [Firmware_burn_1.md](Firmware_burn_1.md) и [Firmware_burn_2.md](Firmware_burn_2.md)).
- В прозрачном режиме AT-команды на этом UART недоступны (их перехватывает p2p-обработчик),
  **то есть `AT+RSSI` пропадёт**. Останутся только прикладные метрики: fps, битрейт, потери.

Есть ещё дешёвый эксперимент на 5 минут: в прошивке модуля присутствует команда `AT+BAUDRATE`.
По документации она задаёт скорость UART0 в прошивке UART-BUS, а не нашего AT-UART, — но если
вдруг она подействует на UART1, то, переключив `SerialAT.begin()` на 460800, вы вчетверо
поднимете fps без всякой перепайки. Проверяется через `examples/AT_test` за пару минут.
